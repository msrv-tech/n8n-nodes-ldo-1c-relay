# Проект поиска документов для LDO 1C

Статус: **реализовано в версии 0.4.0 для ядра 6.8**. Дата: 14 октября 2026.
Относится к [пробелу document-search](../capabilities/README.md#document-search).
Рабочие операции Search Documents и Search Catalog Items добавлены в ноду,
контракт и общий обработчик УНФ/CORE. Статус публикации смотрите в npm; технические отчёты сохраняют исходные версии.
Описание ниже сохраняет первоначальный проект; актуальный интерфейс и политика —
в [руководстве универсального поиска](../search.md).

## Пользовательская задача

Пользователь знает номер, дату, организацию или период, но не UUID документа.
Нода должна найти разрешённые документы, вернуть их ID и версии; следующие
действия читают, изменяют поля или получают PDF без ручного копирования UID.

Два независимых пути:

- Событие 1С → `payload.object.type/id` → чтение документа. Поиск не требуется.
- Внешний запрос/расписание → Search Documents → выбор единственного документа
  или обработка отдельных output items → Get Document Fields / Prepare Document PDF.

## Предлагаемое действие

Resource: **1C Operation**, Operation: **Search Documents**.
Предлагаемое имя команды: `n8n.document.search`, локальный обработчик
`document.search`. Эти имена зарезервированы только этим проектом;
действующий JSON-контракт и allow-list пока не изменяются.

Действие read-only. Все три транспорта используют один обработчик расширения:
своя очередь и MSRV доставляют команду асинхронно, Direct выполняет её через
опубликованный сервис. Смена транспорта не меняет семантику фильтров.

## Параметры

| Параметр | Поведение |
| --- | --- |
| Document Type | Один тип из capabilities, для которого разрешена операция search |
| Number | Необязательный номер; сохраняется как строка с префиксом и ведущими нулями |
| Number Match | Exact по умолчанию; Starts With только если отдельно разрешён политикой |
| Date / Date From / Date To | Один календарный день либо диапазон; эти варианты взаимоисключающие |
| Organization | Необязательный ID организации, выбранный разрешённым способом; не свободное имя метаданных |
| Return All | false по умолчанию; при включении нода проходит страницы в пределах лимита локальной политики |
| Limit | При Return All=false: по умолчанию 20, максимум 50 результатов |
| Cursor | Продолжение предыдущего запроса с теми же фильтрами и политикой |
| Result Mode | List по умолчанию; Single требует ровно одно совпадение |

В первом инкременте нужен хотя бы один селективный фильтр: полный номер либо
ограниченный диапазон дат. Размер диапазона ограничивается локальной политикой,
например 31 день. Prefix требует не менее трёх символов и диапазон дат.
Размер страницы не более 50. Return All также ограничен: например, максимум
200 документов и общий timeout задаются локальной политикой. Если результат
не умещается, вернуть `search_limit_exceeded` и предложить уточнить фильтр;
не выдавать частичный набор под видом полного. Нода собирает страницы до
возврата output items, чтобы превышение лимита не запускало обработку части списка.

Дата означает календарный день в часовом поясе базы 1С. Граница From включена,
To представляется началом следующего дня и исключена. Технический контракт
должен явно различать дату и timestamp; произвольное смешивание времени браузера,
n8n и базы запрещается. Часовой пояс/способ интерпретации публикуется в capabilities.
Конкретное представление даты в wire-схеме уточнить перед реализацией.

Организация допускается только для типов с соответствующим реквизитом. Список
или разрешённый поиск организаций должен иметь отдельное read-разрешение;
существующий write-oriented referenceSearch не расширяется неявно. Пока UI-выбор
организации не реализован, фильтр принимает разрешённый ID из предыдущего шага.

## Результат List

Внутренний ответ API содержит `items`, `has_more`, `next_cursor`. В n8n каждый
найденный документ возвращается отдельным output item, как предусмотрено
[правилами Get Many](../../.agents/nodes.md). Отдельная Split Out не нужна.
Метаданные ограниченной выборки доступны в `_ldo.search` каждого item.

При отсутствии совпадений возвращаются ноль items; downstream шаги не
запускаются. Для отдельной ветки «ничего не найдено» использовать штатную
настройку Always Output Data и IF; пустой служебный item не имеет `object.id`
и не передаётся в запись/PDF. Для webhook с lastNode учитывать поведение n8n
на пустом результате и настроить явный ответ, если нужно вернуть HTTP 200.

Пример одного output item:

```json
{
  "object": {
    "type": "document.СчетНаОплату",
    "id": "00000000-0000-0000-0000-000000000001"
  },
  "revision": "object-version",
  "presentation": "Счет на оплату DEMO-001 от 14.10.2026",
  "values": {"number": "DEMO-001", "date": "2026-10-14T10:00:00"},
  "_ldo": {
    "command_id": "00000000-0000-0000-0000-000000000002",
    "search": {"has_more": false, "next_cursor": null}
  }
}
```

Organization и presentation выводятся только если локальная политика разрешает
их раскрытие. Не возвращать суммы, контрагентов, строки или иные реквизиты
автоматически. Представление может содержать бизнес-данные, поэтому также
должно иметь явное разрешение. Revision пригодна для следующей операции записи.

Порядок фиксирован: дата, затем ID. Продолжение выполняется по последней паре
значений, а не через OFFSET. Cursor содержит границу, отпечаток фильтров,
тип объекта, scope профиля и policy revision. Сервер повторно проверяет всё это
и все ограничения; cursor не предоставляет дополнительных прав. Изменение
политики требует начать поиск заново. Между страницами данные могут меняться:
это последовательное чтение, а не снимок базы на момент первого запроса.

## Результат Single

Для Single применяются те же фильтры, но сервер проверяет до двух совпадений:

- 0 — нормализованный `object_not_found`; прикладная ветка workflow решает,
  что делать дальше.
- 1 — один объект с ID и revision, пригодный для следующей операции.
- 2 и более — `ambiguous_match`; пользователь уточняет дату/организацию.

Никогда не выбирать первый результат автоматически перед изменением документа.
Одинаковые номера у разных организаций или в разных периодах — обычный случай.
Пустые и неоднозначные результаты не запускают запись/PDF по умолчанию.

## Локальная политика 1С

Search — отдельная операция grant, а не побочный эффект разрешения записи
или чтения по известному UUID. Администратор явно разрешает её для типа.
Capabilities публикует разрешённые фильтры, поля результата, режимы поиска,
лимиты и требования селективности. UI показывает только эти варианты.

Обработчик использует штатные права текущего исполнителя и RLS. Запросы
параметризованы; имена объектов и реквизитов получаются из проверенного
каталога и описания адаптации. Запрещены произвольный SQL/BSL, выражение запроса,
имя таблицы, состав полей или ORDER BY от клиента.

Нельзя раскрывать существование недоступных документов через total count,
список вариантов ошибки или presentation. Не выдавать общий размер базы.
Следующая запись повторно проверяет revision и write-grant; результат поиска
не является разрешением изменять найденный документ.

## Отказы и повтор

Предлагаемые причины: `access_denied`, `filter_not_allowed`, `invalid_filter`,
`search_too_broad`, `ambiguous_match`, `cursor_invalid`, `policy_revision_changed`.
Также `search_limit_exceeded` при превышении разрешённого Return All.
Окончательные коды согласовать со схемой ошибок при реализации.

Timeout не означает отсутствие совпадений. Для своей очереди восстановление
использует исходный Command ID и исходные фильтры. Новая страница — новая
команда с cursor. Запись после поиска получает собственный Command ID.

## Воспроизводимые приёмочные сценарии

Подготовка через bridge создаёт только собственные документы с маркером run ID.
Проверяемое действие исполняется настоящей нодой в n8n, результат сравнивается
с независимым чтением 1С. Никакие готовые UUID найденного документа не вводятся
в параметры бизнес-шагов: они берутся из результата Search Documents.

1. Полный номер + дата → один документ → чтение по полученному ID.
2. Номер с ведущими нулями и префиксом не преобразуется в число.
3. Два документа с одинаковым номером: Single отклоняет неоднозначность;
   уточнение даты/организации разрешает её.
4. Отсутствие совпадений: List возвращает пустой массив, Single — ожидаемый отказ;
   ни одна запись не выполняется.
5. Точная граница суток/периода и часовой пояс базы.
6. Пагинация: фиксированный порядок, корректное продолжение, граница Limit.
7. Подмена cursor, фильтров, профиля и policy отклоняется.
8. Отключённый search-grant, неизвестный тип/фильтр и RLS ограничивают результат.
9. Изменение документа после поиска → запись отклоняется по revision.
10. Слишком широкий запрос и попытка передать произвольное имя метаданных.
11. Один набор позитивных/негативных проверок для queue/direct; MSRV требует
    отдельного изолированного enrollment и подтверждения транспортного scope.
12. Cleanup удаляет только собственные fixtures и восстанавливает настройки.

## Последовательность реализации

1. Утвердить wire-схему, grant и правила даты/организации.
2. Реализовать обработчик и настройки capabilities в УНФ, затем действие ноды.
3. Прогнать серверные проверки и пользовательский UI-путь на УНФ.
4. Обновить реестр только после фактической реализации и успешных проверок.
5. Перенести общий код в CORE и отдельно проверить остальные конфигурации.

Рабочий код и серверные проверки выполнены на УНФ 6.8.1.0; общий код перенесён
в CORE 6.8.0.0. Публикация пакета и проверка других конфигураций — отдельные этапы.
